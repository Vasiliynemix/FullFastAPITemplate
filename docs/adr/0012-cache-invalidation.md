# 0012. Инвалидация кэша при мутациях (включая связанные сущности)

## Status

Accepted

## Context

Часть ручек читается по схеме **cache-aside**: сначала кэш (Redis), при промахе —
БД, затем результат кладётся в кэш с TTL. Пример — `GET /users/{id}`:
`UserService` хранит детальную форму юзера под ключом `user:{id}` (TTL 30 c).

Кэш ускоряет чтение, но вводит риск рассинхрона: после изменения данных кэш ещё
держит старое значение до истечения TTL. Особенно коварны **связанные сущности**,
которыми владеет *другой* сервис:

- создание счёта (`AccountService.create_account`) меняет `User.accounts`;
- `deposit`/`withdraw` меняют баланс счёта (он входит в детальную форму юзера);
- `upsert_profile` меняет `User.profile`.

Был реальный баг: после создания счёта `GET /users/{id}` до 30 c возвращал юзера
без нового счёта — `AccountService` не сбрасывал `user:{id}` (он его даже не знал).

## Decision

**Любая мутация данных, которые где-то кэшируются, обязана инвалидировать
соответствующий ключ** — `cache.delete(key)` после успешного коммита. Правило
действует и когда мутация происходит в другом сервисе.

- Ключ кэша владеет сервис-источник и **экспортирует функцию его построения**
  (`user_cache_key(user_id)`), чтобы потребители (напр. `AccountService`) не
  дублировали формат строки и не разъезжались при изменении.
- Зависимый сервис получает `AbstractCache` через DI и зовёт `cache.delete(...)`
  в мутациях, затрагивающих чужие кэшируемые данные.
- Сбрасываем (delete), а не перезаписываем: следующий читатель сам наполнит кэш
  свежим значением (cache-aside), без риска записать частично собранный объект.

Сопутствующее решение про объём данных в ответе — детальная форма (`UserReadDetail`
со связями) только там, где связи нужны (`get`/`list`); базовая (`UserRead`) для
`create`/`update`/`stream`/`register` (не грузим связи зря, см. [ADR 0007](0007-eager-loading.md)).

## Consequences

- Запись чуть дороже (доп. `DELETE` в кэш), зато нет «залипания» устаревших
  данных; читатель всегда получает консистентный ответ максимум через один промах.
- Появляется связность: зависимый сервис знает о ключе чужого кэша (через
  публичную `*_cache_key`). Это осознанный компромисс против дублирования формата.
- Чек-лист при добавлении кэша на чтение: перечислить ВСЕ места (включая другие
  сервисы), которые меняют эти данные, и добавить туда `cache.delete`. Тест на
  инвалидацию обязателен (`test_update_invalidates_cache` как образец).
- При расширении до распределённой инвалидации (события «изменилось X» вместо
  прямого `delete`) — заводим новый ADR, заменяющий этот.
